Pattern: A per-key locking cache (as opposed to one lock guarding the whole cache) for deduplicating expensive computations (embedding, hashing, any pure function of an input key) needs: (1) a fast path -- check the cache under a short-held guard lock, return immediately on hit; (2) on miss, atomically get-or-create a per-key threading.Lock in a pending dict (still under the guard lock, so two threads racing to create the same key's lock get the SAME lock object); (3) acquire that per-key lock (this is where concurrent duplicate requests actually block each other, NOT other keys); (4) double-check the cache again after acquiring the per-key lock (another thread may have finished computing while this one waited) before computing; (5) compute OUTSIDE the guard lock (so unrelated keys aren't blocked during the expensive work); (6) clean up the pending-lock dict entry in a try/finally around the compute call, so a raised exception during computation doesn't leak a lock entry forever (later retries for the same failing key would otherwise all block on a lock nobody will ever release-and-remove). Verified working (not just reasoned about): a 5-thread concurrent test with an artificial 100ms sleep inside the wrapped compute function, asserting the underlying compute is called exactly once for 5 threads requesting the same key.
When: Adding a cache to deduplicate an expensive, deterministic, pure computation (embeddings, parsed configs, expensive lookups) that's redundantly triggered by concurrent or near-simultaneous callers with identical inputs.
Why: A single lock around the whole cache correctness-wise works but serializes ALL computation regardless of key, defeating the purpose of adding concurrency elsewhere in the same system (e.g. thread-per-connection server handling). Per-key locking preserves that concurrency while still deduplicating true duplicates.
