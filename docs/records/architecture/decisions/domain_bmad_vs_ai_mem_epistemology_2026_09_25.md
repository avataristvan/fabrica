Decision: The comparison of BMAD and the ai-mem framework converges on a three-layer picture instead of a 'winner framework': (1) planning artifacts (BMAD PRD/Architecture/Story, or spec-driven development), (2) decision records (ADR-style Markdown files for domain/pattern/anti-pattern), (3) the epistemic mechanism (/reflect Taskly + records + evidence edges + librarian, until 2026-09-26: confidence lifecycle -- see domain_drop_confidence_for_evidence_and_librarian_2026_09_26) — the latter creates the role of the 'project-accompanying developer' and cannot be replaced by either of the other two.

Why:
BMAD structures the handover of tasks within a role pipeline; it solves context loss *within* a pipeline, with no feedback channel and no confirmation/supersession across sessions. Spec-driven development belongs to the same family as BMAD (spec first, code kept in sync, git-native, readable by the team) — not an independent third axis, but the same category 'structured, git-native planning artifact'.

ADRs (just generated in another repo) are the closest match for ai-mem's domain type: Status/Context/Decision/Consequences ≈ Decision:/Why:/Scope:, one file per decision, git-versioned, PR-reviewable, 'superseded by' as the prose equivalent of the supersedes edge. The graphify skill additionally proves that text/JSON in folders instead of a vector DB is generally buildable and productive (graph.json, GRAPH_REPORT.md, one Markdown file per node in obsidian/, retrieval by graph traversal instead of cosine) — but graphify AND ADRs AND BMAD/spec-driven dev all deliver only artifacts at a point in time. None of them has a lifecycle mechanism (something matures through confirmation, fades through refutation, is marked by supersedes instead of deleted) that runs independently of the individual artifact. That is exactly ai-mem's only non-replaceable contribution — the 'project-accompanying developer' is literally this role: an agent whose judgment about planning artifacts and decision records matures, instead of arising anew in every cycle (the junior→senior effect from ai-mem's first account of the method, docs/sources/epistemology_framework.md, formerly docs/epistemology-framework.md).

Devil's advocate 1 (trigger/currency): eval_pull_gap_test_2026_09_20 — in all gap cases mem_query was called 0 times, only the ID pointer in CLAUDE.md worked. Without a solved retrieval trigger, ai-mem pays maintenance costs (/reflect, mem_dream) without collecting the savings. BMAD's redundancy is also a currency guarantee (freshly derived from the current PRD, cannot go stale) — ai-mem entries can go stale before they are marked superseded (domain_direction_judgment_over_scores_2026_09_20: currency beats ranking as a danger). The librarian (todo_bibliothekar_haiku_retrieval_agent_2026_09_25, eval_librarian_2026_09_26) is a first approach against exactly this trigger problem, but still on probation, not solved.

Devil's advocate 2 (team scaling): ai-mem's persistence lives under AI_MEM_PATH (local data directory), per user, per machine, outside the repo. The 'team knowledge' collections are marked [convention]: logical namespaces in ONE local DB, no physically shared storage. No sync/server/export mechanism is documented. BMAD's artifacts are ordinary repo files — git-native, available to every team member. 'Just commit ChromaDB' is not a fix: binary SQLite + vector index segments mean no diff, no merge, no PR review, repo bloat. Team here explicitly means BOTH: human collaborators (potentially on different machines) AND the agent team on one machine — with humans involved, the local-storage gap is real, not hypothetical. (The domain/pattern/anti-pattern subset of it has been solved as git-native Markdown since the ADR migration -- todo_adr_migration_2026_09_25; ChromaDB remains the local, regenerable index on top.)

One practical problem remains despite all this: the retrieval trigger (see above) — neither the storage format nor the ADR migration changes anything about THE FACT that an agent has to look things up. The second open problem originally listed here — the confidence lifecycle fits ADRs, which are effectively immutable, structurally badly — is resolved, not merely mitigated, by dropping confidence/access_count as a trust signal (2026-09-26): there is no longer a mutating number that could collide with immutable ADR files, only edges (confirms/supersedes/contradicts) and a cue, both rare and set explicitly.

Meta-reframing (observation by the Navigator, 2026-09-25): on closer inspection, ai-mem itself is more of a FRAMEWORK/specification (skills, hooks, agent conventions) than a storage solution — ChromaDB is the replaceable part, not the product. The first account of the method (docs/sources/epistemology_framework.md) already opens with exactly this idea ('memory alone does not produce knowledge... the methodology around it'). Concretely, 'ai-mem' splits into two almost independent parts: (1) the framework — when /reflect runs, how trust moves via evidence edges, how collections nest — already lives almost entirely as text (skill prompts, hook code, agent conventions), already git-native; (2) the storage backend — currently ChromaDB, which is what the whole discussion so far revolved around. The 'project-accompanying developer' is the personification of part 1, not of part 2. The ADR migration changes nothing about part 1, only what part 2 hangs on — this separation should guide every future architecture decision ('does this change the framework or only the backend?'). Since 2026-10-14 the framework part is Fabrica (docs/fabrica/core.md and patterns/), see domain_fabrica_practice_not_process_pattern_language_2026_10_14.

Scope: Applies to framework/architecture comparisons and the positioning of ai-mem against BMAD, spec-driven development, ADR practice and graphify, and as a meta-placement of ai-mem's own identity. Recommendation: keep layers 1+2 (planning artifacts, decision records) git-native as text; layer 3 (Taskly/evidence edges + librarian = the framework) remains ai-mem's contribution and should operate on the text artifacts of layers 1+2 instead of on a separate, local ChromaDB copy of the truth. The remaining open problem (retrieval trigger) is an independent engineering task, not solved by changing the storage format.
