---

Rule: Entries written or last edited shortly before a retirement commit silently rot along with it unless someone greps specifically for the affected modules. pattern_load_bearing_entries_require_maintenance_discipline does not catch this automatically, because its grep targets a known old term/threshold — a retirement (module removed or disabled entirely) often leaves behind not a single renamed term but a whole dead call path or a dead threshold, which you only find by searching specifically for the removed module, not for a word. In addition: after every retirement or removal commit, also grep external consumers (~/.claude/agents, ~/.claude/commands, CLAUDE.md files, skills/examples, docs/) — a retirement that is only followed through in the repo itself leaves installed/deployed copies with the old term.
When: After every retirement commit (hook, module or mechanism removed/disabled) — not only after renames or threshold changes, for which pattern_load_bearing_entries_require_maintenance_discipline already applies.
Why: Concretely verified via mem_get in this maintenance batch: automation_session_stats described record_injection as actively called by userprompt_hook.py, although install.py had deregistered this module on 2026-09-13 (arch_decision_userprompt_push_removed_2026_09_13) — the call site had been dead code since then, but the entry text did not say so. pattern_taxonomy_as_quality_gate described ANTIPATTERN_MIN_SCORE/DILEMMA_MIN_SCORE/CONTEXT_MIN_SCORE as currently effective thresholds, although they lived exclusively in the same retired userprompt_hook.py. pattern_injection_caps_not_dumps still recorded the GLOBAL_COLLECTION scan gap as open after it had already been fixed. All three received their now-visible correction (history paragraph or 'is fixed' note) only after an explicit UPDATE batch of this maintenance session — not through the usual grep ritual, because the retirement commit itself was not a threshold/term rename, but a mechanism disappeared completely without a neighbouring entry following it up.

Second case, 2026-09-26 (confidence removal, b5e5d38): the same gap hit ~10 collection entries (key_invariants, arch_overview, hook_system, mempalace_comparison, design_philosophy_junior_to_expert, three pattern_* entries, antipattern_mem_add_metadata_repass, domain_bmad_vs_ai_mem_epistemology_2026_09_25, todo_adr_migration_2026_09_25) AND an external consumer copy: ~/.claude/agents/the-coder.md still described the [available: global] block as 'high-confidence', although since b5e5d38 the gate checks only boost_count ≥ 1. No repo grep would have found this file, because it lies outside the repo — only a targeted grep over the external consumer paths would have.

Third case, 2026-09-29 (rename docs/decisions -> docs/records, 093dc1b): a rename also leaves external consumers behind -- ~/.claude/commands/chunk-plan.md still carried the old path and was corrected on 2026-09-29. The external-consumer grep thus applies to path renames just as it does to retirements.

Case 4 (2026-10-04): Retiring PostToolUse and ChromaDB left ~25 records describing them as current (hook_system, key_invariants, arch_overview, ...) and deployed callers using the now-rejected types (/reflect, /mem-init, the-coder.md). Found by mem_dream and by grepping the callers.
