Decision: mem_dream läuft nach jedem /reflect (Step 6), beschränkt auf die aktive Collection, mode=hier (Haiku-Vorlauf, Sonnet-Synthese), auto_link und auto_supersede an, auto_delete aus. focus_hint nennt die IDs, die in der Session geschrieben, zitiert oder verlinkt wurden. DELETE und MERGE brauchen eine einzige gesammelte Rückfrage; mechanische UPDATE/SPLIT-Anwendung geht an einen Haiku-Subagenten.
Why: Die Eintragszahl (>30) taugt nicht als Auslöser, eine Projekt-Collection bleibt legitim groß (Nutzer, 2026-09-26). Was während einer Session markiert wurde, wird so spätestens beim reflect eingeordnet. Kleine, häufige Dream-Läufe statt seltener riesiger (ein ungescopter hier-Lauf sprengte mit 205k Tokens das CLI-Limit). Arbeit so weit wie möglich an Sonnet und Haiku delegieren (Nutzerwunsch). Bekannter Preis: Dreams eigene mem_get-Lese-Aufrufe (INDEX-Scan, Kandidaten-Volltext) zählen laut key_invariants als deliberate use und stupsen last_accessed_at an — dieselbe Definition, die mem_cleanups Forgetting-Curve (stale_after_days) als 'wurde benutzt' liest. Nach jedem /reflect läuft das jetzt pro Session mindestens einmal, also häufiger als vor dieser Entscheidung: ein Eintrag kann rein durch Dreams eigene Wartungslese-Zugriffe 'frisch' aussehen, ohne dass ihn je ein Agent inhaltlich gebraucht hätte. Nicht gewählte Alternative: Dream-Kandidaten statt Rohanzahl als Auslöser zählen (siehe abgelöste todo_dream_trigger_candidates_not_count_2026_09_25) — hätte den Auslöser genauer gemacht, aber das last_accessed_at-Problem nicht adressiert, da Dream so oder so liest, sobald es läuft.
Scope: skills/examples/reflect.md Step 6, gilt für alle Collections. Bekannter Preis (Scope-Aspekt): Ein auf eine Collection beschränkter Lauf sieht keine anderen Collections, Hochstufungs-Kandidaten nach workspace/global kommen dadurch seltener.
