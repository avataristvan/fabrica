Decision: MarkdownAdrRepository.upsert() now triggers regenerate_index() automatically, but narrowly -- only when an entry's `superseded_by` metadata field actually changes (old file's parsed frontmatter vs. new metadata differ), never on plain creation or a mem_boost-only write.

Why: exodeck-c1 (parallel session, migrating ExoDeck collections to ADR format) reported INDEX.md going stale after `mem_link(..., supersedes)` -- the file itself got `superseded_by` correctly, but INDEX.md's status column stayed 'active' until someone manually ran `mem-adr-sync export`/`reindex`. Root cause: Chunk 3b (docs/adr-migration-chunk-plan.md) deliberately kept regenerate_index() off the per-mem_add path to avoid a read-modify-write race on the one shared file -- correct call for the general case, but it left zero trigger for the specific case that changes a row's status (no cron, no mem_dream hook, nothing). This matters more than cosmetic staleness: the librarian agent (domain_drop_confidence_for_evidence_and_librarian_2026_09_26) judges by reading INDEX.md, so a stale status column could make it treat a superseded entry as still active.

Scope: ai_mem/infrastructure/markdown_adr_repository.py. `_sync_file()` now returns whether `superseded_by` changed; `upsert()` calls a new `_reindex()` helper only when that's true. Both call sites that can set `superseded_by` -- `mem_link` (server.py) and `mem_dream --auto_supersede` (dream_memory.py:531) -- route through `AddEdgeUseCase`'s target upsert (application/add_edge.py:50-56), so both are covered without touching AddEdgeUseCase or either dispatch site, and without reopening the race Chunk 3b avoided (plain creates/boosts still never touch INDEX.md). Tests: test_markdown_adr_repository.py::test_supersede_upsert_regenerates_index, test_boost_only_upsert_does_not_regenerate_index. Full suite: 507/507 passing.
