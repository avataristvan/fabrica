Rule: Every automatic/session-level memory injection point (SessionStart focus, [always-present], per-prompt query hits, expert-collection reads) must use a fixed cap plus a quality gate (confidence/access thresholds) — never scale with the underlying collection's size. Growth in entry count must never translate into growth in per-session token cost.
When: Designing or extending any hook injection point in ai-mem, or proposing a new one (e.g. giving `global` a session-start read moment analogous to `subagent.the-coder`).
Why: Verified by re-reading hook.py: the 'the-coder reads prior patterns at session start' mechanism is NOT a full read of subagent.the-coder — it's `repo.query(expert_collection, _query, n_results=3, ...)` filtered to top 2. Whether that collection has 77 or 770 entries, exactly 2 come out. Same discipline everywhere else already: TOP_K=3 for repo/global hits, _HIGH_CONFIDENCE_MAX=3 for [always-present], plus a hard MAX_TOTAL_CHARS=1500 budget on top. The one place that DOES scale linearly with collection size is `mem-dream`, which sends the full collection text into the consolidation prompt — that's the real cost driver behind pruning duplicates, not per-session injection. Any fix to the known gap that [always-present] never scans GLOBAL_COLLECTION (see repo.ai-mem CLAUDE.md invariants) must reuse this same fixed-cap + confidence/access-gate design, not a browsable full read — otherwise it reintroduces exactly the escalation this principle exists to prevent.
