Rule: Every automatic/session-level memory injection point (SessionStart focus, [available], per-prompt query hits, expert-collection reads) must use a fixed cap plus a quality gate (boost_count ≥ 1, i.e. an explicit /reflect citation) — never scale with the underlying collection's size. Growth in entry count must never translate into growth in per-session token cost.
When: Designing or extending any hook injection point in ai-mem, or proposing a new one (e.g. giving `global` a session-start read moment analogous to `subagent.the-coder`).
Why: Verified by re-reading hook.py: the 'the-coder reads prior patterns at session start' mechanism is NOT a full read of subagent.the-coder — it's `repo.query(expert_collection, _query, n_results=3, ...)` filtered to top 2. Whether that collection has 77 or 770 entries, exactly 2 come out. Same discipline everywhere else already: TOP_K=3 for repo/global hits, _AVAILABLE_MAX=3 for [available] (renamed from [always-present] 2026-07-31; its gate itself dropped confidence/access_count for boost_count-only on 2026-09-26, see domain_drop_confidence_for_evidence_and_librarian_2026_09_26 — the cap-per-injection-point principle here is unaffected by that change, only the gate's composition). The one place that DOES scale linearly with collection size is `mem-dream`, which sends the full collection text into the consolidation prompt — that's the real cost driver behind pruning duplicates, not per-session injection. The GLOBAL_COLLECTION scan gap this entry used to flag as open is fixed: hook.py calls _boosted_entries() a second time against GLOBAL_COLLECTION with its own separate cap, _AVAILABLE_GLOBAL_MAX=2, rendering a distinct '[available: global]' block alongside the repo-scoped one — same fixed-cap + quality-gate design, not a browsable full read. The general principle holds regardless: any new injection point must reuse this fixed-cap + quality-gate design — otherwise it reintroduces exactly the escalation this principle exists to prevent.
